    Nomograms.Nomograms

    source 
    Nomograms

    Build, solve and render nomograms (alignment charts).

    A nomogram is an analog computer printed on paper. Lay a straightedge through the values you know, and it crosses the remaining scale at the answer — no power, no keystrokes, just geometry. It works because its three or more scales are drawn so that any straight line crossing them picks out a solution of an equation. The entire geometric content is d'Ocagne's collinearity criterion,

    | x1  y1  1 |
| x2  y2  1 | = 0
| x3  y3  1 |

    so this package represents every scale as a parametric curve value -> (x, y) and does all its arithmetic by asking where a line crosses a curve. One solver then serves forward and inverse problems alike, and layouts beyond the built-in parallel-axis construction need no new machinery.

    Getting started

    using Nomograms

nom = additive_nomogram(
    Variable(:R1, ReciprocalScale(); domain = (1, 10), label = "R1 (ohm)"),
    Variable(:R2, ReciprocalScale(); domain = (1, 10), label = "R2 (ohm)"),
    Variable(:R, ReciprocalScale(); label = "R (ohm)");
    title = "Resistors in parallel",
)

evaluate(nom; R1 = 4, R2 = 6)          # -> (R1 = 4.0, R2 = 6.0, R = 2.4)
save_svg("parallel.svg", nom; isopleths = [isopleth(nom; R1 = 4, R2 = 6)])

    See additive_nomogram, multiplicative_nomogram, evaluate, isopleth, svg and nomogramplot.

    Nomograms.DEFAULT_ISOPLETH_COLORS

    source 
    DEFAULT_ISOPLETH_COLORS

    Blue, orange, aqua. Three, not more, and in this order: every isopleth on a chart is visible at once, so all three pairs have to stay apart under colour-vision deficiency, and no fourth hue holds up once all pairs are in play. Checked with the validator rather than by eye – worst pair ΔE 9.2 (deuteranopia), 24.0 normal vision, against a ≥8 target.

    The classic d3 category10 palette is not used, for a measurable reason: its orange and green sit ΔE 0.7 apart under protanopia, which is the same colour.

    Nomograms.DEFAULT_ISOPLETH_DASHES

    source 
    DEFAULT_ISOPLETH_DASHES

    Dash patterns cycled one step behind the colours, so a fourth isopleth is a dashed blue rather than a repeat of plain blue. Identity then never rests on hue alone, which is what lets a chart carry more lines than there are safe colours.

    Nomograms.AbstractNomogram

    source 
    AbstractNomogram

    A chart made of Scales on a canvas. Everything about drawing one – ticks, labels, bounding box, both backends – needs only the scales, the canvas and the title, so it is written against this type. What differs between subtypes is how they are solved: a Nomogram is one alignment line through every scale, while a CompoundNomogram is several stages read in turn.

    Nomograms.CompoundNomogram

    source 
    CompoundNomogram

    Several Nomogram stages sharing variables, for relations that need more than three variables.

    Three scales is the limit of a single alignment line, so a four-variable relation is split into two: g(a, b) = t and h(t, c) = d, sharing the intermediate t. The reader lays a line across the first stage to find where it crosses the shared scale, then pivots about that point and reads the second — which is why the shared scale is often called the pivot or turning line.

    Build one with compound, which positions the stages so their shared scales coincide. Drawing works exactly as for a single nomogram; solving propagates values from stage to stage (see evaluate).

    Nomograms.Net

    source 
    Net(u::Variable, v::Variable, surface)

    A two-parameter family of points, surface(u, v) -> (x, y), drawn as a mesh of curves and occupying one of the three slots an alignment line crosses.

    Three collinear points relate three variables. A net carries two of them in a single point, so a chart with a net and two ordinary scales relates four. That is a different construction from compound, which chains stages through a shared pivot, and it reaches relations chaining cannot: a pivot works only when the first two variables combine into one intermediate, whereas a net handles a genuinely two-parameter family.

    Deriving one

    With scale a on x = 0 at height f(a) and scale b on x = 1 at height g(b), a line between them meets x = x₃ at (1-x₃)·f(a) + x₃·g(b). So a net point (x₃, y₃) is crossed exactly when

    α·f(a) + β·g(b) = γ        with   x₃ = β/(α+β),  y₃ = γ/(α+β)

    Any relation whose two net variables enter as the coefficients α, β, γ therefore has a net. The mesh is genuinely two-dimensional as long as (α : β : γ) sweeps a region rather than a curve — when it sweeps only a curve, the net collapses to a line and the relation wanted compound instead.

    See net_nomogram.

    Nomograms.NomogramStyle

    source 
    NomogramStyle(; kwargs...)

    Sizes and thresholds for turning a Nomogram into geometry. All lengths are in chart units – the same units as a nomogram's width and height, which default to 70 by 100 – so one style carries over unchanged between output sizes and backends.

    The defaults follow the proportions of a classic d3 axis: hairline rules, short ticks and small type. At the default pxperunit = 4 a chart unit is 4 pixels, so they come out as roughly 1px strokes, 6px major ticks, 3px of label padding and 10px labels.

    Keywords

    • majorticklength, minorticklength: tick mark lengths.

    • ticklabelgap: gap between a tick's outer end and its label.

    • ticklabelsize, titlesize: text heights.

    • titlegap: gap between the end of an axis and its title.

    • min_major_spacing, min_minor_spacing: a tick is dropped if it would land closer than this to one already placed. This is what keeps a non-uniform axis legible.

    • label_minors: whether minor ticks get labels too.

    • endpoint_ticks: whether to add the ends of each domain as labelled ticks when they fit. An end needing more than three significant figures is left to the axis line: that is a derived reach such as 237.4, not a value anyone chose.

    • ticklabelrotation: :horizontal leaves tick labels upright; :tangent turns each to run along its scale, which reads better on a steep or curved axis.

    • resolve_collisions: whether to drop tick labels that would overlap a label from another scale, and nudge isopleth labels clear of both.

    • avoid_isopleths: whether a tick label struck through by an alignment line is dropped too. A label a line runs across cannot be read, and the tick mark still shows where the value falls.

    • collisionpad: extra clearance required between two labels.

    • axislinewidth, gridlinewidth, tickwidth, isoplethwidth: stroke widths. The grid width applies to the strands of a Net, which are drawn lighter than the scales a reader takes values from.

    • isopleth_overhang: how far an alignment line extends past the outermost scale.

    • markersize: radius of the dot where an isopleth meets a scale.

    Nomograms.ScaleTransform

    source 
    ScaleTransform

    A strictly monotone map from a variable's own units onto the functional axis of a nomogram, together with its inverse.

    A three-variable alignment chart exists whenever the relation can be written in the separable form f1(u) + f2(v) = f3(w); a ScaleTransform is one of those fs. Bundling the inverse with the forward map lets the construction derive the third variable's domain exactly instead of searching for it.

    Implement transform for a new subtype, and either invtransform or hasinverse(::T) = false (in which case inversion falls back to bracketed root finding over the variable's domain).

    Nomograms.TabulatedScale

    source 
    TabulatedScale

    A ScaleTransform known only numerically: values and derivatives at a set of nodes, joined by cubic Hermite interpolation.

    This is what auto_nomogram builds when it derives a transform by integration, since most of those integrals have no closed form worth looking for. With exact derivatives at the nodes the interpolation error is fourth order in the node spacing, far below anything a chart can show. Outside the tabulated range it extrapolates linearly, so a solver probing an ulp past a domain edge gets an answer rather than an exception.

    Nomograms.Variable

    source 
    Variable(name, transform = LinearScale(); kwargs...)

    One variable of a nomogram, before it has been placed on the page.

    Arguments

    • name::Symbol: the keyword used to refer to this variable in evaluate and isopleth.

    • transform::ScaleTransform: the f that this variable contributes to the separable relation f1(u) + f2(v) = f3(w).

    Keywords

    • domain: (lo, hi) in the variable's own units. May be nothing for the result variable of a construction, whose range is then derived from the other two.

    • label: axis title; defaults to string(name).

    • ticks, minorticks: explicit tick values, bypassing automatic selection.

    • tickformat: value -> String.

    • tickstyle: :linear or :log to choose how automatic tick values are picked, or :auto to take it from the transform. A construction may override :auto when it knows better: an N-chart's ratio axis gets logarithmic ticks when it spans a decade or more.

    • side: :left, :right, or :auto (the construction chooses).

    • titleend: which end of the scale the title sits off — :start or :stop for the low or high end of the domain, or :auto for whichever is higher on the page. Worth setting where the automatic choice lands somewhere crowded, as it does for the strands of a Net that converge at one end.

    Nomograms.additive_nomogram — Tuple{Variable, Variable, Variable}

    source 
    additive_nomogram(v1, v2, v3; width = 70, height = 100, title = "", max_modulus_ratio = 4)

    A three-parallel-axis nomogram for the separable relation

    f1(v1) + f2(v2) = f3(v3)

    where each fi is the ScaleTransform carried by the corresponding Variable. v3 is the result variable and is drawn as the middle axis; it may leave domain = nothing, in which case its range is derived from the other two.

    The construction

    Place v1 on x = 0 at y1 = a1 * (f1 - p0) and v2 on x = W at y2 = a2 * (f2 - q0), where [p0, p1] and [q0, q1] are the ranges of f1 and f2 over their domains and a1 = H/(p1-p0), a2 = H/(q1-q0) fit each to the canvas height H.

    A straight line through those two points crosses x = L*W at

    y = (1-L) * y1 + L * y2

    Choosing L = a1 / (a1 + a2) makes (1-L)*a1 == L*a2 == a1*a2/(a1+a2) =: a3, so that

    y = a3 * (f1 + f2) - a3 * (p0 + q0)

    which is exactly a linear scale for f3 = f1 + f2 with gradient a3. Reading a value off the middle axis therefore solves the relation. Because a3 * (1/a1 + 1/a2) == 1, the middle axis spans the same [0, H] as the outer two: its height and position are consequences of the outer scales, not free parameters.

    Keeping the middle axis clear

    The middle axis sits at L = a1 / (a1 + a2) of the way across, so it hugs whichever outer axis has the smaller gradient – the one whose f spans more. Over [1, 1000] against [11, 14] on logarithmic scales the gradients differ about 28-fold, and the middle axis lands 3% of the way across, nearly on top of its neighbour. So the steeper gradient is capped at max_modulus_ratio times the other, by shortening that axis and centring it vertically. An outer axis shifted by d shifts the line's crossing of the middle one by d times that axis's share, L or 1 - L, so the middle axis is shifted to match and every reading is unchanged. The middle axis then lies at least 1/(1 + max_modulus_ratio) of the width from either outer axis: a fifth, by default. The shortened axis loses only resolution it had to spare – it was the one stretched furthest. Pass max_modulus_ratio = Inf for full-height outer axes whatever their ranges.

    Example

    julia> nom = additive_nomogram(
           Variable(:a; domain = (0, 10)),
           Variable(:b; domain = (0, 20)),
           Variable(:total),
       );

julia> nom[:total].domain
(0.0, 30.0)

julia> round(evaluate(nom; a = 3, b = 4).total; digits = 10)
7.0

    Nomograms.align_residual — Tuple{Scale, Any, Tuple{Float64, Float64}, Tuple{Float64, Float64}}

    source 
    align_residual(s::Scale, value, p, q) -> Float64

    Signed area (twice the triangle area) of p, q and point(s, value). Zero exactly when the three are collinear, so this is the residual whose root evaluate seeks.

    This is d'Ocagne's determinant criterion written as a cross product, and it is the only thing a nomogram asserts; every layout in this package is just a choice of scale curves that makes the criterion agree with the relation being charted.

    Nomograms.auto_nomogram — Tuple{Any, Vararg{Any}}

    source 
    auto_nomogram(F, x, y, [z]; kwargs...) -> Nomogram
auto_nomogram(F, x, y, w, ..., z; kwargs...) -> CompoundNomogram

    A nomogram for z = F(x, y) — or z = F(x, y, w, …) with any number of inputs — from the function as you would ordinarily write it.

    Every other constructor asks you to rewrite your formula first — into f₁(u) + f₂(v) = f₃(w), with the transforms chosen and the inverses supplied. This one does that part:

    nom = auto_nomogram((r, n) -> (1 + r/100)^n, :r => (1, 20), :n => (1, 30), :growth)

    Each input is a Variable with a domain, or simply name => (lo, hi), in the order F takes them. The last argument names the result — a Variable or a name — except that with exactly two arguments after F both are inputs and the result is :z. The result's domain is derived from F and, if you give one, checked. Labels, tick formats and explicit ticks on the variables are kept. Transforms are not — deriving them is the point.

    How

    F can be drawn on three straight parallel scales exactly when transforms exist with h(z) = f(x) + g(y). Differentiating shows that requires

    F_x / F_y = f′(x) / g′(y)

    so the test is whether ln|F_x / F_y| splits into a part in x plus a part in y (see separability_defect). When it does, that same identity hands back f′ and g′; integrating them gives f and g, and h follows by walking the level sets of F. The transforms come out as TabulatedScales, and each axis gets linear or decade-based ticks according to how its transform spreads its values.

    Verification

    Whatever the numerics did, the finished chart is then solved over a grid of inputs and every answer compared with F itself. A chart that disagrees by more than rtol of the result's range is never returned — the call throws instead, quoting the error it measured. The chart's relation is F, so relation_residual and max_relation_residual check against your formula rather than the derived one.

    More than two inputs

    One alignment line relates three scales, so F(x, y, w) is drawn as a chain of compound stages and the result is a CompoundNomogram. That needs F to depend on some pair of its inputs only through a single combination of them, t = T(x, y), which holds exactly when F_x / F_y does not depend on w. The first stage then charts t, the second charts z from t and w, and the reader pivots between them on a bare turning line. More inputs are reduced the same way, a pair at a time.

    Every pairing is tried. One can fail for two reasons: F may not depend on the pair through one combination at all, or it may, but with the two stages wanting the intermediate on different scales — (x + y)·w is the standard case, linear in the first stage and logarithmic in the second. That second kind needs a net, which has to be derived by hand (net_nomogram). If no pairing works, the error lists what went wrong with each.

    When it can't

    A formula that is not separable has no three-straight-scale chart at all, and the error says so. It may still have one with a curved scale or a net, but those need a form derived by hand: see determinant_nomogram and net_nomogram. A formula that is not monotone in a variable over its domain fails too, since a straight scale cannot fold back on itself.

    Keywords

    • width, height, title: as for the other constructions. width defaults to 70 for two inputs. In a chain it is the width of the last stage, and the default grows with the chain, 35 per input after the first. An earlier stage always has one input inside the rest of the chain, so it is mirrored and resized, between a quarter of width and width, to land that input mid-way between the axes already there. Every way of pairing the inputs is tried for the first two levels of the chain, and the one whose axes end up furthest apart is kept.

    • rtol = 1e-6: the largest disagreement with F to accept, relative to the result's range.

    Nomograms.compound — Tuple{Vararg{Nomogram}}

    source 
    compound(stages::Nomogram...; title = "", atol = 1e-6) -> CompoundNomogram

    Join nomogram stages into one chart, positioning each so that the scales it shares with an earlier stage lie exactly on top of them.

    Variables are shared by name. Each stage after the first must share at least one with a stage already placed, and that shared scale must carry the same values over the same domain in both — so build the later stage with the domain the earlier one derived:

    first = additive_nomogram(a, b, Variable(:t))          # :t derived
second = additive_nomogram(Variable(:t; domain = first[:t].domain), c, d)
chart = compound(first, second)

    Alignment is a similarity — rotate, scale, translate — chosen to carry the later stage's shared scale onto the placed one, then checked along the whole domain rather than just at the two points that fixed it. A similarity is affine, so it cannot change what any stage computes.

    The shared scale is drawn once. Note that the stages generally interleave rather than sitting side by side: a parallel-axis construction puts its result between its two inputs, so a pivot shared by two such stages has both stages' other scales straddling it. project will reshape the result if the arrangement is awkward.

    Nomograms.determinant_nomogram — Tuple{Vararg{Pair}}

    source 
    determinant_nomogram(var => curve, var => curve, var => curve, ...; kwargs...)

    A nomogram from scales given directly as curves, fitted to the canvas for you.

    This is the general form. Every three-variable nomogram is a set of parametric curves positioned so that d'Ocagne's determinant

    | x₁(u)  y₁(u)  1 |
| x₂(v)  y₂(v)  1 |  =  0
| x₃(w)  y₃(w)  1 |

    vanishes exactly when the relation holds. additive_nomogram and ratio_nomogram are two particular solutions of that condition; this constructor takes any other one you can write down, including curved and concurrent layouts that no arrangement of parallel axes can express.

    Each argument is a Variable paired with a function from its value to a point. The curves may be written in whatever coordinates are natural for the geometry: their combined bounding box is measured and mapped onto width × height. Collinearity survives any affine map, so the fit cannot change what the chart computes – including the anisotropic one used by default to fill the canvas.

    Keywords

    • width, height: the canvas to fit to.

    • preserve_aspect: fit with one scale factor and centre the result, rather than stretching each axis to fill.

    • relation: the algebraic relation, if you have it, for relation_residual and max_relation_residual to check the geometry against. Optional – the chart draws and solves without it.

    • title, nsamples: chart title, and how finely curves are sampled when measuring the bounding box.

    Every variable must declare a domain: with no distinguished result there is nothing to derive one from.

    Example

    The parallel-axis construction, written out by hand in its natural coordinates. Scales at x = 0, 2 and 1, with the middle one at half scale, encode u + v = w; the fit then stretches that 2 × 10 sketch onto the full canvas.

    julia> nom = determinant_nomogram(
           Variable(:u; domain = (0, 10)) => u -> (0.0, u),
           Variable(:v; domain = (0, 10)) => v -> (2.0, v),
           Variable(:w; domain = (0, 20)) => w -> (1.0, w / 2);
           relation = (u, v, w) -> u + v - w,
       );

julia> round(evaluate(nom; u = 3, v = 4).w; digits = 10)
7.0

julia> point(nom[:v], 10)
(70.0, 100.0)

    Nomograms.evaluate — Tuple{CompoundNomogram}

    source 
    evaluate(cn::CompoundNomogram; values...) -> NamedTuple

    Solve a compound nomogram by reading its stages in turn.

    Supply enough variables that some stage has exactly one unknown; that stage is solved, its answer becomes known, and the pass repeats until everything is determined. Which variables you supply is up to you, as long as the chain closes — the intermediate on a shared scale is usually left to be derived, but it can equally be an input.

    Throws, naming what is left, if the values given are not enough to finish.

    Nomograms.evaluate — Tuple{NetNomogram}

    source 
    evaluate(nn::NetNomogram; values...) -> NamedTuple

    Solve a net chart. Supply three of its four variables.

    Which problem this is depends on which variable is unknown. With both net variables known the net contributes a single point and it is the ordinary three-point alignment. With one of them unknown the line is already fixed by the two scales, and the answer is where that line crosses the strand for the known net variable — a curve, which a line may cross more than once. As elsewhere, evaluate refuses to choose between several and evaluate_all returns them.

    Nomograms.evaluate — Tuple{Nomogram}

    source 
    evaluate(nom::Nomogram; values...) -> NamedTuple

    Solve the relation by alignment. Supply every variable but one and the remaining one is read off its scale; the result is a NamedTuple of all variables.

    Because the solver only ever asks "where does this line cross that scale", forward and inverse problems are the same call — any one of the variables may be the unknown.

    Throws if the alignment line crosses the unknown's scale more than once, which only a curved scale can do; evaluate_all returns every solution instead.

    Example

    julia> nom = additive_nomogram(
           Variable(:a; domain = (0, 10)),
           Variable(:b; domain = (0, 10)),
           Variable(:s),
       );

julia> round(evaluate(nom; a = 2, s = 9).b; digits = 10)
7.0

    Nomograms.log_ticks — Tuple{Real, Real}

    source 
    log_ticks(lo, hi) -> (majors, minors)

    Ticks for a logarithmic axis: every whole mantissa 1–9 in every decade the range touches, offered as a major, with tenths between them as minors.

    There is deliberately no cut-off for wide ranges. majors comes back in the order thin_ticks should try them — decades, then 5s, then 2s, then the rest — and thinning keeps whatever fits. So a crowded axis settles on decades alone, a less crowded one on the classic 1-2-5 sequence, and a roomy one labels every mantissa, all from the same candidates. A fixed rule counting decades could only ever pick one of those, and picked decades-only for an axis spanning a hair over two.

    Every mantissa is also offered as a minor, so one whose label is dropped still gets a tick mark. On a range too narrow to hold three whole mantissas — 100 to 200 holds only its ends — the tenths are promoted to majors as well, since otherwise almost nothing is labelled.

    Nomograms.max_relation_residual — Tuple{NetNomogram}

    max_relation_residual(nn::NetNomogram; n = 7) -> Float64

    The worst disagreement between a net chart's geometry and the algebra it claims to encode.

    Sweeps both net variables over an n × n grid and the first scale over n values, solves the second scale geometrically, and checks each answer against the relation. Inputs whose alignment line misses a scale are skipped; NaN comes back when there is no relation to check or nothing in the sweep could be solved.

    Nomograms.max_relation_residual — Tuple{Nomogram}

    source 
    max_relation_residual(nom::Nomogram; n = 9) -> Float64

    The worst disagreement between a nomogram's geometry and the algebra it claims to encode, over a grid of n × n inputs.

    Getting a determinant form right is the hard part of designing a nomogram by hand, and a chart that is subtly wrong still draws perfectly well. This solves the first two variables against the third geometrically and then asks relation_residual whether the answer satisfies the relation; anything far from zero means the curves and the formula disagree.

    Returns NaN for a nomogram built without a relation. Inputs for which the alignment line misses the third scale are skipped, since those say nothing about correctness.

    Nomograms.multiplicative_nomogram — Tuple{Variable, Variable, Variable}

    source 
    multiplicative_nomogram(v1, v2, v3; width = 70, height = 100, title = "", max_modulus_ratio = 4)

    f1(v1) * f2(v2) = f3(v3)

    julia> nom = multiplicative_nomogram(

           Variable(:y; domain = (1, 10)),
           Variable(:z),

(1.0, 100.0)

    Nomograms.net_nomogram — Tuple{Net, Pair, Pair}

    source 
    net_nomogram(net::Net, a => curve_a, b => curve_b; kwargs...) -> NetNomogram

    A four-variable chart: a Net carrying two variables, and two ordinary scales given as curves, in the manner of determinant_nomogram.

    Everything is written in whatever coordinates suit the geometry and fitted to the canvas together; collinearity survives the affine fit, so it cannot change what the chart computes. The net's surface is moved by the same fit as the scales.

    Keywords

    • width, height, title, preserve_aspect, nsamples: as for determinant_nomogram.

    • relation: the algebraic relation (u, v, a, b) -> residual, for max_relation_residual to check the geometry against.

    Example

    The general quadratic a·x² + b·x + c = 0. Written as a·x² + b·x = -c, the coefficients are α = x², β = x, γ = -c, so the net in (x, c) is

    x₃ = x/(x² + x) = 1/(1 + x)        y₃ = -c/(x² + x) = -c/(x·(1 + x))
    julia> nom = net_nomogram(
           Net(
               Variable(:x; domain = (0.5, 5)),
               Variable(:c; domain = (0, 4)),
               (x, c) -> (1 / (1 + x), -c / (x * (1 + x))),
           ),
           Variable(:a; domain = (0.5, 3)) => a -> (0.0, a),
           Variable(:b; domain = (-6, 0)) => b -> (1.0, b);
           relation = (x, c, a, b) -> a * x^2 + b * x + c,
       );

julia> [round(s.x; digits = 8) for s in evaluate_all(nom; a = 1, b = -3, c = 2)]
2-element Vector{Float64}:
 1.0
 2.0

    Nomograms.project — Tuple{Nomogram, AbstractMatrix}

    source 
    project(nom::Nomogram, H::AbstractMatrix; kwargs...) -> Nomogram
project(nom::Nomogram, src => dst; kwargs...) -> Nomogram

    Reshape a nomogram by a projective map, without changing a single answer it gives.

    A projective map sends straight lines to straight lines, so it preserves the one thing a nomogram asserts: that a point from each scale is collinear. Everything else about the picture is free. That is what makes reshaping a design tool rather than a risk — a region where the ticks are piled on top of one another can be pulled open, and the chart still computes exactly what it computed before.

    The second form builds the map from four point correspondences via projective_transform, which is usually how you want to say it: give the corners of a quadrilateral in the current chart and where they should end up.

    The result is re-fitted to the canvas, since a projective map takes the bounding box somewhere arbitrary. The composition of that affine fit with the projective map is still projective, so the guarantee is unaffected.

    Keywords

    • width, height: canvas for the reshaped chart; defaults to the original's.

    • preserve_aspect, nsamples: as for determinant_nomogram.

    • title: defaults to the original's.

    Example

    julia> nom = additive_nomogram(
           Variable(:a; domain = (0, 10)),
           Variable(:b; domain = (0, 10)),
           Variable(:s),
       );

julia> skew = project(nom, [(0, 0), (70, 0), (70, 100), (0, 100)] =>
                           [(0, 0), (70, 20), (70, 80), (0, 100)]);

julia> round(evaluate(skew; a = 3, b = 4).s; digits = 10)
7.0

    Nomograms.projective_transform — Tuple{Any, Any}

    source 
    projective_transform(src, dst) -> Matrix{Float64}

    The 3×3 homography taking the four points src to the four points dst, each given as a 4-tuple (or vector) of (x, y).

    Four correspondences fix a projective map exactly, which makes this the practical way to describe one: say where you want four corners to land rather than writing out nine coefficients. No three of the four source points may be collinear, nor of the destination.

    Nomograms.ratio_nomogram — Tuple{Variable, Variable, Variable}

    source 
    ratio_nomogram(v1, v2, v3; width = 70, height = 100, title = "")

    An N-chart (also called a Z-chart) for the ratio relation

    f1(v1) / f2(v2) = f3(v3)

    Two vertical scales joined by a diagonal, which is where the result is read. v3 may leave domain = nothing, in which case the range it can reach is derived from the other two. All three transforms must be strictly positive over their domains.

    Why not a parallel chart?

    multiplicative_nomogram already charts ratios, by taking logarithms. The N-chart earns its place by needing no logarithm at all: the scales stay linear, so precision is even along them and small ratios are not squeezed into a corner. It is the layout to reach for when the quantities are everyday ones – a rate as distance over time, a concentration, a unit conversion – and the reader wants to interpolate by eye.

    The construction

    Put v1 on x = 0 at y1 = a1 * f1, running up from the bottom-left corner, and v2 on x = W at y2 = H - a2 * f2, running down from the top-right. Take the diagonal between those two corners, D(s) = (sW, sH). A line through a point on each outer scale meets the diagonal where

    s = a1*f1 / (a1*f1 + a2*f2)

    Writing r = f1/f2 and k = a1/a2 that is s = k*r / (k*r + 1), a one-to-one map from the ratio onto the diagonal: reading s back gives r = s / (k * (1 - s)).

    Note what the two scale factors do not have to be. The usual textbook derivation makes them equal and the ratio falls out directly; here the diagonal's own scale absorbs k instead, so each outer axis is free to be fitted to the canvas on its own. Taking a1 = H/max(f1) and a2 = H/max(f2) anchors the diagonal at the two corners, which is what gives the layout its N.

    The diagonal is drawn only over the part its scale actually reaches, f1/f2 between min(f1)/max(f2) and max(f1)/min(f2), so it stops short of the corners – those are the ratios 0 and infinity.

    Example

    julia> nom = ratio_nomogram(
           Variable(:distance; domain = (1, 10)),
           Variable(:time; domain = (1, 10)),
           Variable(:speed),
       );

julia> nom[:speed].domain
(0.1, 10.0)

julia> round(evaluate(nom; distance = 6, time = 3).speed; digits = 10)
2.0

    Nomograms.separability_defect — Tuple{Any, Any, Any}

    source 
    separability_defect(F, xdomain, ydomain; n = 9) -> Float64

    How far z = F(x, y) is from being drawable on three straight parallel scales. Zero (to rounding) when transforms f, g, h exist with h(z) = f(x) + g(y); otherwise the largest violation found on an n × n grid.

    The test is the classical one: such transforms exist exactly when ln|F_x / F_y| splits into a function of x plus a function of y. Rather than take a mixed second derivative of that — numerically noisy — this checks the equivalent identity

    L(x, y) − L(x, y₀) − L(x₀, y) + L(x₀, y₀) = 0

    which needs only first derivatives. Throws if F is not monotone in each variable, since then no straight scale can carry it whatever the transforms.

    Nomograms.solve_all_on — Tuple{Scale, Tuple{Float64, Float64}, Tuple{Float64, Float64}}

    source 
    solve_all_on(s::Scale, p, q) -> Vector{Float64}

    Every value on scale s whose point lies on the line through p and q, in increasing order. Empty when the line misses the scale.

    A straight line can cross a curved scale more than once, so "the" solution is not always well defined. Checking only the sign of the residual at the ends of the domain – the usual shortcut – would report no solution for an even number of crossings and pick an arbitrary one of an odd number, so the whole domain is searched instead.
